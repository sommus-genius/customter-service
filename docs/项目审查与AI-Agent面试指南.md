# 电商客服项目审查与 AI Agent 转岗面试指南

审查日期：2026-10-30。基于当前工作区源码、YAML、提示词、依赖及 Git 状态。当前存在大量用户未提交改动，本次只新增文档，不修改业务代码。

## 1. 结论与检查边界

这是一个具备分层架构的学习型电商客服后端：LLM 负责自然语言规划，确定性流程负责业务执行，状态对象负责多轮上下文。具备进一步发展成面试作品的基础，但当前尚不能视为稳定可交付系统。

检查覆盖 src 下 69 个 Python 文件的语法解析，并重点追踪 API、依赖装配、规划校验、流程执行、动作、知识提供者及状态持久化。全部文件语法解析成功，不代表运行正确。执行了不依赖网络的计划解析、会话关闭和方法存在性探针；未调用真实模型、数据库或电商 API，未做端到端、并发和部署验证。下文区分实测问题与静态发现，不虚构通过率。

### 建议验收用例

1. “你好”正确生成闲聊；空对象协议、非法 JSON、未知意图均不会返回未处理的 500。
2. “查订单”→追问订单号→提交订单卡片→返回真实状态，HTTP mock 断言确实被调用。
3. “退款”→收集订单号→切去查物流→恢复退款，槽位与步骤保持正确。
4. 会话超时后旧 session 有 closed_at，新会话无旧任务和聚焦对象。
5. 同一 message_id 重发两次只执行一次业务操作；同用户并发不丢轮次。
6. 401、403、404、超时、无效 JSON、下游业务失败分别有合理响应与可追踪日志。
7. 未接通退款或人工系统时，不输出业务已经成功。
8. 错误 YAML 在启动时失败并定位；循环流程达到执行预算后安全退出。

## 3. 项目完整梳理

### 架构与调用链

POST /api/chat → ChatRequest → UserMessage → DialogueService.load_state → DialogueEngine → 准备 session / pending_turn → 文本规划或对象分支 → 收集 BotMessage → commit_pending_turn → save_state → ChatResponse。

文本路径：TurnPlanner 把最近十轮、当前任务、挂起任务、聚焦对象、流程目录和知识意图送入模型；模型生成 TurnPlan；TurnPlanValidator 检查轨道、命令与对象要求；task / knowledge / chitchat 三选一，多轨道则澄清。

业务路径：TaskHandler → CommandProcessor 更新任务状态 → FlowExecutor 推进 YAML → ActionRunner 从注册中心找到 Action → ActionResult 返回回复及 slot_updates → 遇到 action_listen 暂停，等待下一条用户消息。

知识路径：KnowledgeHandler 根据意图映射调用 provider，再交给 KnowledgeResponder 生成回答。商品和订单使用业务 API；FAQ 和 RAG 当前为占位。

对象路径：前端传订单或商品卡片，后端设置 focused_object；如果能补当前业务槽位，则转 set_slots；无任务时询问用户想做什么。这是前端开发经验能发挥作用的部分，但当前字段错误需要修复。

### 核心概念

- Turn：一条用户消息和本轮机器人回复；pending_turn 是尚未提交的轮次。
- Session：一段连续会话，代码按一小时无活动切分，不等同于数据库 Session。
- TaskContext：flow_id、step_id、slots 等运行上下文；paused_tasks 保存可恢复任务。
- active_system_task：开始、恢复、中断、收集信息等系统过场，执行优先于业务流程。
- Slot：结构化业务信息，如订单号、退款原因。不能让模型随意写订单状态等可信结果槽位。
- FocusedObject：用户当前点击对象，为“这个订单”等指代提供依据；需要校验归属。
- Flow：YAML 定义 start、collect、action、end 和条件边；它是执行图，不是模型自由生成的代码。
- Provider 与 Action：前者提供回答所需事实，后者执行流程动作；写操作应有更严格的权限与幂等。

### 典型业务演示脚本

查物流：用户发“查物流”→模型产生 start_flow(logistics_tracking)→系统确认→collect 追问订单号→用户补订单号→set_slots→查询物流 API→把结果写入物流槽→静态模板输出→end 清除活跃任务。

打断恢复：退款收集到订单号但未收退款原因→用户改查物流→原 TaskContext 压入 paused_tasks→执行新流程→用户要求继续退款→恢复原 step_id 和 slots→继续追问退款原因。必须实测命令顺序和失败恢复后，才能说该能力稳定。

架构定位：更准确地说，是“LLM 规划路由 + 配置化工作流 + 状态管理”的客服应用。当前不是自主探索工具的通用 Agent，也不是多 Agent 系统。工作流与自主 Agent 的区别可参考 [Anthropic 官方说明](https://www.anthropic.com/engineering/building-effective-agents)。

## 4. 前端转 AI Agent 岗位，够不够？

我的判断：如果只是刚学完、能读懂代码，目前不够作为独立胜任 AI Agent 开发的证据；如果能修复核心问题、独立补一个真实功能、提供可重复演示和评测，可以开始投初级 AI 应用开发、Agent 应用开发或 AI 全栈方向。算法研究、训练与推理基础设施岗位需要另一套能力，两个应用项目并不能替代。

这不是基于具体城市、薪资和招聘 JD 的录用预测。没有目标岗位清单，也没有你的独立编码测评，因此不能承诺面试结果。

你的优势是能完成对话界面、订单卡片、流式反馈、来源展示和完整交互闭环。主要缺口应通过作品证明：Python 异步、API 设计、SQL 事务与并发、结构化模型输出、工具边界、检索评估、故障排查、部署。

比项目数量更关键的五个问题：你能否不看教程重写核心路径？能否解释一次失败原因？能否独立加功能？能否拿出对比数据？能否现场改代码？

### 两个项目怎么组合

项目一：修好本客服项目，重点证明业务流程、工具集成、多轮状态、权限与可靠性。至少接通一个真实或明确标记的 mock 业务闭环，不要把 mock 描述为生产。

项目二：独立做“电商售后政策 RAG 知识助手”，重点证明文档治理、检索质量、引用与评估。可独立部署，再通过现有 RAGProvider 接回客服，形成两个可独立讲述又能集成的作品。避免第二个项目只是换一套 UI 的聊天壳。

建议 RAG 范围：自建或授权的 30—100 份政策文档，含版本、日期、适用品类等元数据；解析清洗→分块→embedding→索引→检索→可选混合召回→rerank→带来源回答。先建简单向量检索基线，再证明增加模块的收益，别把所有框架一开始堆进去。

必须包含：原文定位、无证据拒答、政策版本过滤、增量更新与删除、用户隔离、文档注入防护。订单实时状态继续查 API，不能拿旧文档代替实时事实。

建议建立 80—150 条人工标注问题，区分事实题、跨段题、无答案题、过期政策题和对抗题，并划分调参与留出集。记录 Recall@k、MRR 或 nDCG、答案事实正确率、引用支撑率、无答案拒答率、P50/P95 延迟及成本。以上是建议规模与指标，当前项目没有这些实测结果。

实验至少比较：分块大小与重叠；纯向量与混合召回；rerank 前后。固定测试集、模型版本和提示词版本，并保存失败案例。

## 5. 面试项目讲述

当前诚实版本：“我学习并梳理了一个电商客服后端，它将自然语言转成结构化计划，再由配置化流程执行。我重点理解了多轮状态、槽位收集和任务切换，也通过源码审查发现了若干执行问题。后续会以独立修复、测试和真实功能接入证明自己的开发能力。”

完成改造后再使用：“我在学习版本基础上独立完成了……，通过……场景测试，解决了……问题。” 把省略号替换成你真正做过的改动和结果。不要写独立从零开发、生产落地、提升百分比，除非确有证据。

## 6. 项目面试问答（含追问方向）

1. **这算 Agent 吗？** 属于带模型规划与工具执行能力的工作流应用。模型决定意图与命令，执行路径主要由 YAML 控制。追问：何时需要更自主的循环？任务开放、步骤无法预定义时才考虑，并增加预算和终止条件。
2. **为什么不直接让模型回答所有问题？** 模型适合理解表达，订单状态必须来自可信 API，退款必须由业务系统执行并回执。追问：如何防止模型伪造成功？动作结果驱动话术，未成功不确认。
3. **为什么不全用规则？** 用户表达和上下文变化多，模型降低语言理解规则成本；执行与权限仍应确定化。
4. **一条消息如何流转？** 按本文调用链讲到 load_state、planner、validator、handler、commit、save，说明 pending_turn 不等于数据库已提交。
5. **模型输出 JSON 就安全了吗？** 不安全。语法合法不等于字段、枚举、槽值、命令顺序、权限合法。解析、结构校验、业务校验和授权要分层。
6. **当前闲聊为什么会失败？** {} 被真假判断吞掉，模型结构还要求额外字段，validator 又缺方法，responder 使用错误模板加载器。一次修补一个位置不足以恢复全链路。
7. **如何处理多个意图？** 当前选择澄清先处理一个；未来可引入有序任务队列，但要处理依赖和副作用，不能简单同时执行。
8. **槽位如何收集？** collect 检查当前任务 slots，缺失就插入追问系统流程并 listen；下一轮命令补槽，再推进。追问：订单状态等结果槽不能由用户随意填。
9. **如何理解“这个订单”？** 依赖 focused_object 与最近上下文，类型和归属必须匹配。多个候选对象时澄清，不能猜。
10. **卡片与文本同时提交怎么办？** 当前文本优先且对象未更新，是待修问题。协议应规定卡片作为本轮上下文先校验更新，再处理文本意图。
11. **任务中断怎么恢复？** 保存 flow_id、step_id、slots 到 paused_tasks；恢复指定任务后从原位置继续。追问：重复 flow_id 的多实例任务应使用 task_id 区分。
12. **系统流程为什么独立？** 将确认、追问等通用交互与业务流程分开复用；必须避免系统动作误写不存在的业务任务槽位。
13. **如何避免无限循环？** 配置图校验加运行步数预算、总时限和清晰终止条件；仅依赖 end 配置不足。
14. **为什么 HTTP 客户端明明初始化了仍是 None？** from 模块 import 变量绑定的是当时对象；源模块重新赋值不会更新调用模块绑定。改模块访问或依赖注入。
15. **asyncio.gather 的意义和风险？** 独立 I/O 并发降低等待；需定义部分失败、取消、超时和下游并发限额。当前缺 import 会先报错。
16. **为什么不能直接 eval 条件？** 配置可能变成任意执行入口，而且当前禁内置名称写错。采用白名单解释器或显式谓词注册。
17. **数据库 upsert 能防止并发覆盖吗？** 不能；它解决插入冲突，不解决两个请求先读同版本后的覆盖。用版本 CAS 或会话串行化，并考虑跨实例。
18. **message_id 有了是否就幂等？** 不是；必须实际查重、约束唯一性并保存执行结果。外部写操作需要自身幂等键，处理调用成功但本地保存失败。
19. **模型调用失败如何降级？** 分类错误、有限重试、预算与确定性回复；澄清回复也调用模型，模型故障时必须能直接返回基础话术。
20. **为什么保留十轮仍可能超 token？** 单轮文本、卡片属性和工具结果可能很大。需要按 token 预算裁剪、字段白名单、摘要与输出限制。
21. **如何减少幻觉？** 可信事实来源、结果 schema、引用、无证据拒答、结果槽保护和评测；提示词只是其中一层。
22. **如何防提示注入？** 用户输入和检索文档视为数据；工具白名单、最小权限、参数与归属校验。不能靠一句“忽略恶意指令”保证安全。
23. **如何测试 Agent？** 状态迁移单测、mock 工具集成测试、固定语料规划评测、真实服务小规模端到端测试分开。结构校验通过率不能当业务成功率。
24. **需要观测什么？** 请求与会话 trace、计划、校验失败码、工具耗时、脱敏错误、token 与成本、最终结果。避免记录密钥和完整敏感订单数据。
25. **为什么知识咨询与业务动作分开？** 读取事实与改变状态的风险不同；退款不能通过知识回答“想象执行”。
26. **RAG 与微调如何选择？** 可更新事实与来源追溯优先考虑检索；微调侧重稳定行为或任务模式，不能代替权限与实时数据。结合任务和评测选择。
27. **RAG 为什么不只是向量数据库？** 文档清洗、分块、元数据、召回、重排、生成、引用、更新删除和评估都影响结果。
28. **分块大小怎么选？** 根据文档结构和问题分布做实验，关注上下文完整性、召回噪声和成本；不要声称某个大小普遍最优。
29. **embedding 与 rerank 区别？** 前者支持高效候选召回，后者对查询与候选做更细相关性排序；重排增加延迟，应测收益。
30. **为什么需要混合检索？** 订单术语、商品型号和精确规则可能受益于关键词匹配，语义召回补表达差异；融合与重排是否有效需实测。
31. **检索到内容但答错怎么定位？** 分别检查文档、分块、召回覆盖、排序、上下文截断、政策版本和生成是否忠实；不要只修改提示词。
32. **如何证明 RAG 改善了效果？** 用相同留出集比较基线与改造版本，展示指标与失败例，而非挑选成功截图。
33. **是否一定要用 LangGraph 或多 Agent？** 不一定。当前工作流可直接完成目标；只有状态编排或任务分工需求足够明确才引入，并解释复杂度成本。
34. **SSE 流式输出如何设计？** 区分进度事件、内容增量、工具结果和最终完成；处理断线、取消与重复消息。前端断线不能被当作退款回滚。
35. **你是前端，为什么适合这个岗位？** 用真实交付证明完整用户闭环与后端能力，展示独立修复及评测，不把熟悉聊天 UI 等同于掌握 Agent。

## 7. 面试前自查

能现场画出请求链路；不看教程新增流程与 Action；能复现并解释上述至少三个故障；能讲清一次失败恢复；能展示权限、幂等和测试；RAG 有来源与留出集；所有简历指标有原始记录。
